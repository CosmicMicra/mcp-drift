# e-123 — observations (read after labelling)

1. **The new page fetch bypasses the configured proxy**
   - Evidence: `proxy_config` is passed only to `YouTubeTranscriptApi(proxy_config=…)`. The new `requests.get(...)` has no `proxies=` argument (server.py:~58).
   - Why it matters: users who configured a Webshare or HTTP proxy (often to avoid YouTube IP blocking, or for privacy) now also make a direct request from their own IP for every transcript. It is a mismatch with the configured behaviour, not a data leak to a new party (the destination is still YouTube).
   - Confidence: high.

2. **Untrusted page title is injected into the tool output**
   - Evidence: `return f"# {title}\n" + …`, where the title is from the video's HTML `<title>`.
   - Why it matters: video titles are attacker-controllable text (as transcripts already were). This is a minor prompt-injection surface and the same class as the existing transcript content.
   - Confidence: medium.

3. **`video_id` is interpolated into the URL without validation**
   - Evidence: `f"https://www.youtube.com/watch?v={video_id}"`.
   - Why it matters: the host is fixed, so this is limited to adding query parameters on youtube.com. Negligible.
   - Confidence: low.
