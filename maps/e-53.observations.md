# e-53 — observations (read after labelling)

1. **File writing existed before; the new voice-track feature adds more writes of the same kind**
   - Evidence: old `assemble()` wrote the MP4 via ffmpeg (unchanged); new `voiceTrack()` writes `<dir>/<output_name>-voice.wav` and a temp dir (assemble.ts:141-200).
   - Why it matters: the change is consistent with the stated purpose (laying narration over a film). The tool description does not mention `voice_lines`, but the parameter schema documents it.
   - Confidence: high.

2. **`project` name `..` may escape the output root**
   - Evidence: core.ts:17 `projectDir = (project) => resolve(OUTPUT_ROOT, project.replace(/[^\w.-]+/g, "_"))`. Dots are allowed, so `project: ".."` resolves to the parent of `~/flow-mcp-out` (the home directory).
   - Why it matters: an AI-supplied project name could make the tool write `final.mp4` / `final-voice.wav` (fixed extensions) in the home directory. Impact is limited by the fixed extensions and sanitised file name. This is pre-existing and not introduced by this change.
   - Confidence: medium (static reading; not executed).

3. **Arbitrary input-file reads**
   - Evidence: `voice_lines[].file`, `clips`, `music`, `voiceover` accept any absolute path, checked only with `existsSync` (assemble.ts:152; 209).
   - Why it matters: ffmpeg reads any file the user can read, but only media decoding output is produced. The risk is low and matches the purpose.
   - Confidence: low.

4. **Process execution uses `execFile` with argument arrays (no shell)**
   - Evidence: assemble.ts:9 `const run = promisify(execFile);`
   - Why it matters: AI-supplied values reach ffmpeg argv and filter strings only as numbers (`toFixed`) or paths. There is no shell interpolation.
   - Confidence: high.
