# e-113 — observations (read after labelling)

1. **Unauthenticated localhost WebSocket bridge to a browser-control extension**
   - Evidence: ws-client.ts:23 `new WebSocketServer({ port, host })` with no `verifyClient`/origin check; ws-client.ts:26-30 accepts any connection and replaces the current one.
   - Why it matters: browsers do not apply CORS to WebSocket connections, so any web page the user visits (or any local process) can try to connect to `ws://127.0.0.1:18080`. If it connects, it displaces the extension, receives the AI's requests (URLs, text being typed, which may include credentials), and can return forged page snapshots or tool results to the AI. Native messaging, used in the old version, was restricted to the registered extension.
   - Confidence: medium (static; exploitability depends on timing and the extension reconnect logic, which was not traced).

2. **Transport change is not reflected in tool descriptions or README security notes**
   - Evidence: tool descriptions unchanged; only the CLI help says "communicates with the Chrome extension via a localhost WebSocket connection".
   - Why it matters: users approving the server are not told that a network listener now exists.
   - Confidence: medium.

3. **Positive: the native-messaging host files are no longer written**
   - Evidence: installer.ts removed `writeFileSync(manifestPath, …)`, the wrapper script, and `chmodSync`. The extension dropped the `nativeMessaging` permission.
   - Confidence: high.

4. **Extension has `<all_urls>` and uses the user's live sessions (pre-existing)**
   - Evidence: packages/extension/manifest.json `"host_permissions": ["<all_urls>"]`; README "access to the user's logged-in sessions, cookies".
   - Why it matters: this raises the impact of finding 1.
   - Confidence: high.
